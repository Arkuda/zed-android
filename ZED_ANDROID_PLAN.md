## Контекст

Интеграция для установленного штатного локального Zed на Windows, Linux и macOS: отдельное окно существующего AVD, выбор приложения и варианта, сборка, запуск и отладчик Kotlin/Java. Эмулятор во вкладке, форк Zed и NDK не нужны. Основной Windows smoke — настоящий `D:\git\phosphor_impl` в установленном Zed 1.29.3: у него **одно** приложение `:app`, поэтому отдельно нужен тест с несколькими модулями. Граница записи: обычные результаты Gradle (`build/`, `.gradle/`, `.kotlin/`) допустимы, никаких собственных файлов, даже игнорируемых, плагин в Android-проект не пишет.

## Что взято из Android Studio и что отличается

[AndroidRunConfigurations](https://github.com/JetBrains/android/blob/8682e7aa88e8e153d3aea8dbf7308785babe7d90/android/src/com/android/tools/idea/project/AndroidRunConfigurations.kt#L71-L100) после обновления модели отбирает app-модули и не создаёт вторую конфигурацию для уже привязанного модуля. Это не «найти все MainActivity»: [тест Studio](https://github.com/JetBrains/android/blob/8682e7aa88e8e153d3aea8dbf7308785babe7d90/android/project/testSrc/com/android/tools/idea/project/AndroidRunConfigurationsTest.kt#L67-L107) ожидает одну конфигурацию и когда Activity приходит из библиотеки. Берём разделение **приложение / вариант / устройство**, но не файлы `.idea` и не индекс IntelliJ. [Studio ранжирует варианты по default build type/flavor, затем debug](https://github.com/JetBrains/android/blob/8682e7aa88e8e153d3aea8dbf7308785babe7d90/project-system-gradle-sync/src/com/android/tools/idea/gradle/project/sync/DefaultVariants.kt#L27-L78); здесь намеренно показываем реальные варианты пользователю, не утверждаем идентичный автоподбор. [DefaultApkActivityLocator](https://github.com/JetBrains/android/blob/8682e7aa88e8e153d3aea8dbf7308785babe7d90/android/src/com/android/tools/idea/run/activity/DefaultApkActivityLocator.java#L61-L145) работает с APK для target device и итоговым ID. Мы получаем эквивалентную границу **после установки** через Package Manager; при нескольких launcher не подставляем первый, даём выбрать.

## Подход

1. Использовать [Debugger Extension API](https://zed.dev/docs/extensions/debugger-extensions), [глобальные задачи](https://zed.dev/docs/tasks) и [глобальный сценарий](https://zed.dev/docs/debugger#global-debug-configurations). Корень расширения пуст; создать dev extension с `extension.toml`, Rust `cdylib`, `zed::register_extension!` и схемой DAP. Установка через `zed: install dev extension`; не регистрировать Java/Kotlin как новые языки, не требовать активного Kotlin-файла. Локальный CLI отдельно от WASM; открытие проекта не запускает Gradle и не пишет на диск от имени интеграции.

2. Однократная настройка **пользовательского профиля**, не Android-проекта. Создать npm-пакет `zed-android-tools` в `tools/`, `bin: {"zed-android":"bin/zed-android.cjs"}`, Node 22+. В каталоге самого плагина: `npm ci`, `npm link`, `zed-android setup`. Никаких `init` на проект, `.zed/`, `.vscode/`, `.idea/`, `.gitignore`, `.git/info/exclude`, правок `local.properties`, Gradle-скриптов или Git-хуков. Глобальные `tasks.json` и `debug.json` брать из config dir Zed ([`paths::tasks_file` / `debug_scenarios_file`](https://github.com/zed-industries/zed/blob/main/crates/paths/src/paths.rs)): `%APPDATA%/Zed`, `${XDG_CONFIG_HOME:-~/.config}/zed` на Linux, `~/.config/zed` на macOS; `setup --config-dir <absolute-directory>` для отдельного профиля (каталог открытого **глобального** `zed: open tasks`). Не использовать cwd либо project tasks в качестве fallback; отказаться, если config dir разрешился внутрь Android-проекта. Нужные записи: `Android: Select application` → `zed-android select`, `Android: Start emulator` → `zed-android emulator`, `Android: Build` → `zed-android build`, `Android: Run` → `zed-android run`. Для всех `cwd: "$ZED_WORKTREE_ROOT"`, args отдельными значениями; Build/Run получают `save: "all"`. Глобальный `debug.json`: `{"label":"Android: Debug","adapter":"Android","request":"launch"}`; отдельная build-задача не нужна, DAP запускает ту же цепочку на сохранённых исходниках. Глобальные команды могут отображаться и вне Android: проверять корневой `settings.gradle[.kts]` и Wrapper перед Gradle и выдавать ясное сообщение.

   Merge обеих глобальных JSONC-конфигураций через `jsonc-parser`, сохраняя чужие записи, комментарии и формат; сначала проверить обе целиком. Идентичная запись → ничего не менять; другой объект под тем же `label`, невалидный JSONC или неверный тип корня → показать конфликт, ничего не перезаписывать. Создавать только недостающие записи; атомарная замена каждого изменённого файла; повторный `setup` побайтно идемпотентен. Не запускать setup автоматически при открытии окна. Пользовательское состояние отдельно: `%LOCALAPPDATA%/zed-android`, `~/Library/Application Support/zed-android`, `${XDG_STATE_HOME:-~/.local/state}/zed-android` соответственно для Windows/macOS/Linux. Под `projects/<sha256(canonical-root)>/` хранить `target.json` (module, variant, настройки launcher/processName для этой пары) и `device.json` отдельно; файлы менять атомарно, отмена выбора не меняет предыдущий выбор. Журналы старта AVD и служебные данные только во внешнем каталоге. Не сохранять PID, порты JDWP или credentials как настройки.

3. Выбор AVD: наследовать окружение пользователя, не подменять расположение AVD расположением SDK. SDK брать из `local.properties` (`sdk.dir` с Java-properties escaping, включая пример `sdk.dir=E\:\\android_sdk`), затем `ANDROID_HOME`, затем совместимый `ANDROID_SDK_ROOT`, иначе найти SDK по настоящему `platform-tools/adb` в PATH. Не использовать `ANDROID_SDK_HOME` как путь SDK. Имена инструментов с `.exe` на Windows. Искать `emulator/emulator` только для команды эмулятора; SDK-платформы, образ и AVD пользователь устанавливает отдельно. При отсутствии нужного инструмента назвать его и проверенный путь.

   `emulator -list-avds` — источник имён, не обход `~/.android`. При нескольких вариантах показать в терминале Zed нумерованный список и принять выбор; при одном запустить его, при нуле — объяснить, что нужно создать AVD, при отмене ничего не запускать. Сначала сравнить имя с ответами `adb -s <emulator-serial> emu avd name` у запущенных эмуляторов. Если найден — использовать существующий; иначе запустить `emulator -avd <имя>` отдельным процессом с GUI (не `-no-window`, не `-qt-hide-window`), дать окну пережить завершение задачи. Опрашивать выбранный AVD, а не первый `adb devices`; дождаться `device` и `getprop sys.boot_completed` == `1`, не дольше 180 секунд. При раннем выходе/тайм-ауте показать причину и путь к журналу старта; не убивать чужой эмулятор и не стирать его данные.

4. **Модуль → вариант → устройство — независимые решения.** Для `select`, Build, Run и DAP launch получать актуальную модель доверенного Gradle root. Внешний `tools/gradle/android.init.gradle`: зарегистрировать `:zedAndroidTargets` и через `gradle.beforeProject`, `pluginManager.withPlugin('com.android.application')`, `androidComponents.onVariants` собрать только действительные пары `project.path + variant.name` с `variant.applicationId` и отладочностью фактического build type из Android DSL (не `name.endsWith("Debug")`). Вызов Wrapper `--init-script <absolute path> --no-configure-on-demand --no-configuration-cache --console=plain :zedAndroidTargets` из корня; task action отдаёт ровно одну JSON-строку `ZED_ANDROID_TARGETS:`. Конфликт имени служебной задачи/сбой модели → ошибка без подмены. `apply false` в root, библиотеки, test-only и dynamic-feature модули не являются отдельными приложениями. Учитывать вложенные Gradle paths, переопределённый projectDir, плагины-конвенции, flavors и отключённые AGP-варианты; не искать `app/`, APK или текст `include()` по дереву. Не полагаться на вывод `gradle tasks` или имя открытого файла.

   Первый Build/Run/Debug: один модуль → выбрать автоматически; несколько → показать все полные пути (например `:phone:app`, `:wear:app`), **не выбирать первый**. Затем варианты выбранного модуля с именем и applicationId; предложить точный `debug` по умолчанию, при нескольких вариантах дать явный выбор, при единственном принять его. При Debug разрешать только debuggable-варианты, не переключать обычную Run-цель молча. Явный `Android: Select application` всегда открывает терминальный список для смены, с отметкой действующей пары; последующие команды используют сохранённую пару только после точного сравнения со свежей моделью. Пропавшая цель, изменённая ветка → показать выбор заново; отсутствие приложений → сообщение без сборки. Отмена → никакой сборки/деплоя. В первой версии это выбор из `task: spawn` в терминале Zed, не заявлять нативный тулбар Android Studio. Перед сборкой/установкой показывать `<module> / <variant> / <applicationId>` и для деплоя serial. Для параллельных окон передавать снимок выбора конкретной команды далее неизменным, не перечитывать общий «последний выбор» на стадии установки.

   В DAP-процессе нельзя читать ответы пользователя из stdin (там протокол). Только когда нужен выбор, использовать обратный DAP `runInTerminal` (`kind: "integrated"`, argv = абсолютные `process.execPath`, собственный CLI entry, `pick`, путь к запросу). Передать меню с непрозрачными ID через уникальный каталог `mkdtemp` вне проекта, закрытый для других пользователей; CLI атомарно публикует там ID либо отмену, адаптер проверяет ID по исходному набору и удаляет каталог при завершении. Один каталог на один запрос — никакого общего файла «следующий debug target». Не посылать произвольные команды от worktree. При отсутствии client capability, закрытии терминала или через 180 с — явная отмена без запуска, предложить `Android: Select application` и повторить F4. В обычных задачах тот же picker напрямую через stdin/TTY; не читать ввод при единственном валидном варианте.

   `build` вызывает только `<module>:assemble<CapitalizedVariant>`; устройство не требуется. Для `run` и DAP launch — одна общая функция `deploy(root, target, serial, output)`; вызвать **за один Gradle-процесс** `<module>:install<CapitalizedVariant>` и новую `<module>:zedAndroidDescribe<CapitalizedVariant>` с `ANDROID_SERIAL` равным одному проверенному онлайн-serial. Стандартная AGP install-задача сама собирает и выбирает APK для устройства, не склеивать все APK из каталога. Describe-задача через Provider возвращает `variant.applicationId`, существующие исходные корни `variant.sources.java` и `variant.sources.kotlin` и `projectDir` в JSON-строке с префиксом `ZED_ANDROID_VARIANT:`. Использовать предоставленный Wrapper из каталога проекта (`gradlew.bat`/`./gradlew`); для Windows передавать bat и массив аргументов через `cross-spawn`, не собирать shell-строки из путей/настроек; task path получать только из валидной пары, корневой модуль `:` не удваивать. Код возврата Gradle, отмена, исчезнувший вариант, отсутствующая модель или APK/подпись несовместимы → показать причину и остановиться, не запускать старую установку и не делать uninstall.

   Между discovery и build могла смениться ветка. Внешний init script получает выбранные module/variant как данные и перед запуском task graph требует **точное** существование пары и совпадение `applicationId`; не предоставлять Gradle возможность подобрать сокращённое имя соседнего модуля. `--init-script` и опции discovery не записывать в пользовательские `gradle.properties` или `~/.gradle/init.d`. Для отладки Activity из собственной библиотеки включать корни только разрешённых проектных зависимостей runtimeClasspath выбранного варианта, сопоставив атрибуты разрешённого варианта с моделью библиотек (`com.android.library`/`androidComponents`). Библиотека при этом не появляется в picker приложений. Если у двух источников остаётся один ключ package/file и нельзя отличить его по runtime line table, показать unresolved, а не исходники соседнего приложения.

5. После Start сохранить `{avd,serial}` во внешнем `device.json`. Явный `ANDROID_SERIAL` должен обозначать ровно одно подключённое устройство в состоянии `device`; иначе ошибка. Затем — проверенный сохранённый serial с перепроверкой имени AVD, затем единственная online-цель, при нескольких — предложить выбрать из `adb devices -l`, а не первый результат. Если сохранённая цель исчезла, потребовать нового выбора; `offline`/`unauthorized` не подходят. До выбора и при отмене не устанавливать. После успешного deploy запросить `adb -s <serial> shell cmd package query-activities --components --user current -a android.intent.action.MAIN -c android.intent.category.LAUNCHER -p <applicationId>`. Один компонент (включая alias) → запуск; ноль → «установлено, нет launcher activity»; несколько → показать список, сохранить `component` под выбранной парой во внешнем состоянии и каждый раз проверять по свежему списку. Run: `adb -s <serial> shell am start -W --user current -a android.intent.action.MAIN -c android.intent.category.LAUNCHER -n <component>`; вывести package/component/serial, текст Android и ошибку при `Error:` или неуспешном status. Не хватать Home/Wallpaper/Service вместо launcher, не менять HOME role, разрешения или настройки устройства.

   Проверять также `android.intent.category.LEANBACK_LAUNCHER` отдельным запросом (не обе категории в одном intent); объединять по component, запоминать подходящую категорию для `am start`. При двух категориях одного component использовать обычную LAUNCHER. Нулевая выдача не исключает модуль из Build. Путь к исходнику в DAP канонизировать для сопоставления и возвращать в написании **открытого** worktree для UI. Для эмулятора разбирать имена AVD отдельно от stderr, отбрасывать диагностику вроде `INFO | Storing crashdata …` даже в stdout; не подавлять настоящие ошибки старта.

6. Хост расширения: корневой `Cargo.toml` с `zed_extension_api = "=0.7.0"`, `[debug_adapters.Android]` в `extension.toml`, `debug_adapter_schemas/Android.json` для `request: "launch"`. Реализовать `get_dap_binary` и `dap_request_kind` согласно [Extension API](https://docs.rs/zed_extension_api/0.7.0/zed_extension_api/trait.Extension.html). Не возвращать `Launch` при ином или отсутствующем request. `DebugAdapterBinary`: stdio (`connection: None`), `cwd` из `worktree.root_path()`, `envs` из `worktree.shell_env()`, исходный JSON в `request_args.configuration`. При явном `user_provided_debug_adapter_path` запускать этот исполняемый DAP-сервер напрямую. Обычно запускать найденный `worktree.which("node")` с аргументами `[entry,"dap"]`: на POSIX `entry` — найденная npm bin-ссылка `zed-android`; на Windows взять каталог найденного `zed-android.cmd` и составить соседний `node_modules/zed-android-tools/bin/zed-android.cjs` по [структуре npm global](https://docs.npmjs.com/cli/v11/configuring-npm/folders/). Собирать Windows-пути как пути **хоста**, а не рассчитывать на WASI `Path::parent` для обратных слешей. Не запускать `.cmd` как DAP binary. Если Node/CLI не найден — подсказать `npm ci`, `npm link` и проверку PATH из терминала Zed. DAP stdin/stdout только для кадров протокола; весь вывод Gradle/SDK — как DAP `output` либо stderr.

7. Для `zed-android dap` переиспользовать не приложение VS Code, а Android/JDWP-ядро и DAP-обработчики **MIT** из [adelphes/android-dev-ext, cb6c780](https://github.com/adelphes/android-dev-ext/tree/cb6c78070cf7fd9c431a9999518fac312ff26b5c/src). В `tools/vendor/android-debug/` взять транзитивно используемые модули из `src/`, сохранить оригинальный `LICENSE`, точный commit и учёт локальных изменений. Вход — `DebugSession.run(AndroidDebugSession)` из `@vscode/debugadapter`; не тащить extension host, старый postinstall, langserver, APK-декодер, VS Code picker, аналитику и дамп `process.env`. Закрепить используемые npm-зависимости lockfile; не качать произвольный код при F4.

   Заменить upstream `launchRequest` общим `deploy`, разрешением launcher из шага 5 и адресным `adb -s <serial> shell am start -S -D --user current -n <component>` **без `-W`**: процесс может ждать отладчика до `onCreate`. Дождаться точного PID процесса приложения (по умолчанию `applicationId`, для нестандартного `android:process` — полный `processName` в пользовательском `target.json` для выбранной пары; при ошибке вывести путь к этому файлу) и его появления в JDWP на том же serial; тайм-аут 30 с → ошибка с package, serial и подсказкой о debuggable-варианте. Не брать первый PID из `adb jdwp`. Подключать `Debugger.attachToProcess` с `AttachBuildInfo`, но для Zed отвечать на **launch**. Форвард `adb -s <serial> forward tcp:0 jdwp:<pid>`, сохранить выданный порт вместо upstream диапазона с коллизиями. После присоединения отправить `initialized`, принять breakpoints, дождаться `configurationDone`, ответить на launch и только тогда resume. Ошибка → один отрицательный DAP response и `terminated`; на Stop/EOF/ошибке снять только собственный forward, закрыть сокеты, не оставлять приложение ждать debugger (при отмене незавершённого launch остановить именно запущенное приложение). Не убивать adb-сервер или эмулятор.

   Для breakpoint и stack frame использовать один индекс **файлов**, построенный из реальных исходных корней выбранного варианта (шаг 4), не старый `Map<package,одна папка>`/`app/src/main` и не предположение «имя класса равно имени файла». Сопоставлять package, JDWP `SourceFile`, line tables и фактический путь `.java`/`.kt`, включая `FooKt`, внутренние классы и ещё не загруженные классы через ClassPrepare; неоднозначную или неисполняемую строку не выдавать за проверенную. Подключить существующие обработчики upstream для `threads`, `stackTrace`, `scopes`, `variables`, step in/over/out и continue. Стек и переменные извлекать из ART, не из статического анализа. В этой интеграции отладчик работает с отладочной информацией установленной сборки, не обещать восстановление вырезанных оптимизатором строк или значений.

## Критические места в исходниках адаптера

- `src/debugMain.js`: `launchRequest`, `setBreakPointsRequest`, `stackTraceRequest` — подключить общее развёртывание и один файловый индекс в обоих направлениях.
- `src/debugger.js`: не использовать `startDebugSession` с fallback на последний JDWP PID; в `disconnect` убрать вызов `host:killforward-all`, даже на ошибке рукопожатия.
- `src/adbclient.js`: заменить старую пару forward/unforward на создание системным adb и `adb -s <serial> forward --remove tcp:<свой порт>`.
- `src/debugger-types.js`: в `DebuggerBreakpoint` убрать обязательное совпадение имени класса с basename файла; у одного исходного breakpoint может быть несколько runtime locations — снимать все вместе.
- `src/utils/print.js`: никакого `console.log` в DAP-процессе. Проверять поток кадров даже при ошибке запуска.

## Проверка

1. В корне расширения — `cargo build --locked --target wasm32-wasip2`; в `tools/` — `npm ci`, `npm test` (`node --test`), `npm link`. Матрица Windows/Linux/macOS проверяет запускаемый из другого cwd с пробелами CLI, сохранение чужой JSONC-задачи/комментария, конфликт label без изменения обоих профильных файлов, повторный `setup` без записи. Подставлять временный **внешний** профиль, не трогать персональные конфиги при автоматическом тесте.
2. **Реальный Phosphor, установленный Zed.** Windows PowerShell: `$env:JAVA_HOME='C:\Program Files\Java\jdk-17'`; `$env:ANDROID_HOME='E:\android_sdk'`; `$env:ANDROID_AVD_HOME='E:\android_sdk\.android\avd'`; `$profileDir=Join-Path $env:TEMP ("zed-android-"+[guid]::NewGuid())`; `zed --user-data-dir $profileDir --new D:\git\phosphor_impl`; настроить глобальные файлы этого профиля `zed-android setup --config-dir "$profileDir\config"` и `zed: install dev extension` на каталог плагина. Существующие буферы пользователя не сохранять и не менять. `task: spawn → Android: Select application` показывает только `:app` и реальные `debug/release`; выбрать `debug`. Build без устройства → `:app:assembleDebug` и debug APK; Start emulator → `Pixel_9`, отдельное видимое окно и тот же serial при повторном Start. Run → `dev.phosphor.launcher/.MainActivity` на выбранном AVD, видна панель Phosphor. `adb -s <serial> shell pidof dev.phosphor.launcher` возвращает PID. Сравнить default HOME через `cmd package resolve-activity --brief -a android.intent.action.MAIN -c android.intent.category.HOME` до и после, не нажимать «всегда», не выдавать разрешения от имени пользователя. Если пакет с тем же ID имеет другую подпись — не удалять; тестировать на отдельном временном AVD той же системы.
3. Без редактирования Phosphor: поставить breakpoint в `app/src/main/java/dev/phosphor/launcher/MainActivity.kt:58` на `frame = FrameLayout(this)`. F4 → `Android: Debug` из уже запущенной `singleTask` Activity обязан остановиться в **новом** `onCreate`, показать `this`, Step Over → `dock = Dock(this)`, Continue → видимое приложение. Учесть launcher- и HOME-фильтры одной Activity, Wallpaper/Notification services не цели запуска. Перед F4 создать контрольный `adb -s <serial> forward tcp:0 tcp:12345`; после Stop проверить `adb forward --list`: контрольный сохранился, JDWP-форвард сеанса исчез; убрать только контрольный порт. На двух устройствах проверить по `pm path`, что новый пакет тестовой фикстуры отсутствует на невыбранном устройстве.
4. **Чистота репозитория проверяется отдельно от успешной сборки.** До/после полного сценария сравнить вывод `git --no-optional-locks -C D:\git\phosphor_impl status --porcelain=v1 --untracked-files=all`, не требовать чистого исходного состояния. Проверить и то, что Git скрыл бы: во внешнем каталоге зафиксировать список файлов/каталогов с относительными путями и хеши файлов до/после, включая hidden/ignored; исключить `.git` и штатные build-каталоги (`.gradle`, `.kotlin`, `build` у корня и `app/build`). `.gitignore`, `.git/info/exclude` и существующий `local.properties` сравнить побайтно. Список, контент и git status вне штатных build-артефактов неизменны; особенно `.zed`, `.vscode`, `.idea`, state, logs, init scripts. Не обходить проверку удалением созданных файлов или изменением ignore.
5. **Несколько приложений доказываются отдельно**: сформировать маленькую временную Gradle-фикстуру вне пользовательской репы, с тем же wrapper/AGP/Kotlin, `:phone:app` и `:wear:app`, `:shared` (`com.android.library`), у двух app разные ID `example.phone` и `example.wear`, flavor `staging` с `applicationIdSuffix=".staging"`; у второго module нестандартный `projectDir`, у первого — отключённый через `beforeVariants` `stagingRelease`. В Gradle поместить комментарий с неверным `applicationId`. Первый Run и первый F4 отдельно при пустом пользовательском состоянии: список содержит два полных Gradle path, без `:shared` и отключённой пары. Выбрать `:wear:app / stagingDebug` → устанавливается только `example.wear.staging`, открывается UI с надписью Wear, остановка в исходнике Wear. Перезапустить Zed — выбор сохранился; переключить на Phone → надпись и стек Phone. Удалить выбранный модуль **только в фикстуре** → повторный выбор, не автостарт другого. Cancel → прежнее состояние и ноль установок. Два разных Gradle root с одинаковыми именами модулей не делят предпочтения.
6. На той же внешней фикстуре: добавить в выбранной Activity Kotlin `onCreate` вызов top-level `answer(21)` и Java `Probe.twice(21)` из одного package, но разных исходных корней; `answer` возвращает `x+1`, `twice` присваивает `int result=value*2` и возвращает `result` на отдельной строке. Реальные breakpoint в обеих функциях → правильные файлы, видны `x=21` и `result=42`. Проверять доступный Linux/macOS desktop аналогично: нативный SDK, JDK проекта, AVD соответствующей архитектуры; ни локальный Windows smoke, ни матричные проверки CLI не называть GUI-проверкой трёх ОС.

### Регрессии из открытых issues VS Code

Это сообщения о наблюдаемом поведении, не доказательство единой первопричины и не результаты проверки Zed. Отработать на отдельной фикстуре:

- [adelphes #76 — flavors](https://github.com/adelphes/android-dev-ext/issues/76) и [React Native Tools #3068 — закомментированный applicationId](https://github.com/microsoft/vscode-react-native/issues/3068): доказательство — проверка `example.wear.staging` и чужого ID выше, не просто список Gradle tasks.
- [adelphes #108 — запуск до окончания сборки](https://github.com/adelphes/android-dev-ext/issues/108): в фикстуре заменить видимую метку A на B и задержать сборку; один Run должен показать B. При остановленном пакете внедрить ошибку компиляции в фикстуру → ни Run, ни F4 не запускает прежний APK.
- [adelphes #147 — activity-alias](https://github.com/adelphes/android-dev-ext/issues/147): launcher объявить только alias в flavor manifest, activity может прийти из `:shared`. Два alias, включён один → Run запускает включённый, Debug доходит до `onCreate`. Оба включены → выбор, выключение сохранённого alias → повторное разрешение, а при нуле Build остаётся доступен.
- [adelphes #139 — breakpoint после загрузки класса](https://github.com/adelphes/android-dev-ext/issues/139): до установки breakpoint один раз нажать кнопку; поставить breakpoint в уже исполненном обработчике и нажать снова → остановка на нужной строке, видна локальная переменная. Удалить breakpoint → следующее нажатие без остановки.
- [Dart-Code #3896 — symlink и пути редактора](https://github.com/Dart-Code/Dart-Code/issues/3896): это отчёт Flutter, не диагноз ART. Открыть fixture через symlink/junction, проверить тот же breakpoint и Step Over без открытия дубликата вкладки по физическому пути.
- Смежный случай, **не открытый баг**: [DiemasMichiels/emulator #59](https://github.com/DiemasMichiels/emulator/issues/59) закрыт по неактивности, а не с доказанным исправлением. Вывод `-list-avds` с двумя именами и диагностической строкой → только два пункта. На настоящем SDK подтвердить выбранное имя через `adb -s <serial> emu avd name`; если SDK не печатает шум, тест парсера и реальный запуск отчитывать отдельно.
